# PR-009 Admin Dashboard, Issues and Analytics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a staff-only `/ops` area that includes:

- authenticator-protected access with roles;
- an issues inbox with the full evidence and actions that never move money;
- an append-only audit log;
- anonymous first-party health and visibility analytics;
- a manual Market page.

**Architecture:**

- **Postgres** (migrations 0017+) holds staff, roles, TOTP, ops sessions, audit, issues, analytics and market entries.
- **API:** `/v1/ops/*` routes sit behind the recipient session plus an ops grant (a second cookie) plus a per-route permission. The public route `POST /v1/events` receives allow-listed analytics events.
- **Worker:** turns outbox events and scheduled detectors into issues, auto-resolves cleared ones, and rolls up analytics daily.
- **Web:** `/ops/*` pages; a tiny analytics sender in the public and recipient pages.

**Tech Stack:** existing pins only. TOTP and AES-GCM use `node:crypto` (RFC 6238 implemented in-house; no new dependency). Charts are hand-made SVG. The QR library (`qrcode`, already pinned) shows the enrolment code.

**Spec:** `docs/superpowers/specs/2026-10-19-pr009-admin-analytics-design.md`

## Global Constraints

### Permissions

- The full set: `issues.view`, `issues.resolve`, `pages.suspend`, `recoveries.cancel`, `analytics.view`, `market.edit`, `audit.view`, `payments.recheck`, `private.view`.
- Owner holds all of them. Only Owner is seeded.

### Owner grant and enrolment

- `pnpm ops:grant-owner --phone <number>` creates the staff role and prints a one-time enrolment code (valid 30 min; stored hashed).
- Authenticator enrolment requires that code.

### TOTP

- RFC 6238: HMAC-SHA1, 6 digits, 30-s step, ±1 step.
- The last used step is stored; a code from that step or earlier is refused (no reuse).
- The secret is encrypted with AES-256-GCM, key `OPS_TOTP_KEY` (32 bytes, base64; required by the API).
- 5 wrong codes → ops access locked for 15 min.

### Ops grant

- Cookie `tipme_ops`: HttpOnly, SameSite=Lax, Path=/, Secure unless local. The token is 256-bit and stored as SHA-256.
- Bound to the recipient session id: signing out, or the session being revoked, ends the grant.
- Expires 12 h after creation, or after 1 h idle.

### Ops routes

- Every `/v1/ops/*` route requires all of:
  - the recipient session;
  - the ops grant (except the enrolment and grant-opening routes);
  - the route's permission;
  - the CSRF guard on non-GET routes.
- Non-staff or missing grant → 404 `NOT_FOUND` (reveals nothing). Staff without the permission → 403 `FORBIDDEN`.

### Staff accounts and recovery

- Email recovery is refused for staff: the request still answers `sent`, but no mail is written.
- A phone change, or a completed recovery, on a staff account deletes their TOTP enrolment and ops grants.

### Audit

- `audit_events` is append-only, with triggers.
- Each event records: staff user id, action, permission, subject type/id, reason (required for changes and reveals), trace id, time.

### Private data

- Supporter messages, supporter names, phone numbers and emails are redacted in all ops responses.
- They are returned only by `POST /v1/ops/issues/:id/reveal {reason}` (permission `private.view`), which is audited.

### Admin actions never move money

- No refunds and no ledger writes from ops.
- "Re-check" only asks the provider (PR-006 reconciliation for one subject).

### Suspension

- Sets `profiles.status='suspended'` plus `suspended_reason`, and revalidates the page.
- The recipient can still sign in, sees a banner with the reason, cannot set the page live, and can still withdraw.
- In-flight tips settle normally. No new moments or rewards are created while suspended.

### Issues

- Status is `open` or `resolved`. The resolver is a staff user or `system`.
- Auto-resolved when the cause clears. A recurrence opens a new issue.
- Dedupe key per source: `event.<outbox dedupe key>`, `stuck_tip.<tipId>`, `unmatched.<id>`, `recovery.<id>`.

### Analytics

- `ANALYTICS_ENABLED` (API) defaults to `true` unless `NODE_ENV=production`, where the default is `false`.
- **Accepted events:**

  | Group               | Events                                                                                                                                         |
  | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
  | Profile and tipping | `profile_viewed`, `tip_cta_clicked`, `amount_selected`, `custom_amount_entered`, `message_started`, `payment_started`                          |
  | Payment outcome     | `payment_pending`, `payment_failed`, `tip_completed`, from the server only                                                                     |
  | Arrival             | `qr_scanned`                                                                                                                                   |
  | Recipient activity  | `recipient_shared_link`, `qr_downloaded`, `qr_printed`, `report_shared`, `moment_shared`, `recipient_first_tip` (server), `recipient_returned` |

- **Properties** (strict schema, so no free text):
  - `surface` (enum `profile|checkout|status|dashboard|qr|report|moments`);
  - `channel` (enum `qr|link|instagram|x|facebook|whatsapp|search|direct|other`);
  - `handle` (handle pattern);
  - `returning` (boolean).
- The client sends nothing when `navigator.globalPrivacyControl === true` or `doNotTrack === '1'`.
- The flow id is random per tab (`sessionStorage` key `tipme.flow`). The returning flag is `localStorage` key `tipme.seen` = `'1'`.
- The server stores the device class (`mobile|desktop`) and the minute bucket. The IP and user agent are never stored.
- Raw events are kept 90 days. Daily rollup into `analytics_daily`.
- Rate limit: 120 events per minute per client.

### QR codes

- Recipient QR codes encode `/@handle?src=qr`. The canonical URL stays `/@handle`.

### Time zone

- Africa/Lagos for days and weeks.

### Gates

- No Git: one checkpoint per task (format, lint, typecheck, test, plus `db:migrate`, `test:integration` and `test:e2e` where touched).
- No new dependencies.

## Review Focus

1. **An ops grant must die with its recipient session.**
   - Sign out, or revoke the device, and `/v1/ops/*` → 404 even with the old `tipme_ops` cookie.
   - Pinned in Task 2.
2. **TOTP code reuse and clock skew.**
   - The same code twice → refused the second time.
   - The previous or next step → accepted.
   - Two steps away → refused.
   - Pinned in Task 1.
3. **A signed-in non-staff recipient probing `/v1/ops/*`** gets 404 everywhere and nothing is audited as theirs. A staff member without `private.view` calling reveal → 403.
   - Pinned in Task 2 and Task 4.
4. **Analytics payloads carrying personal data:**
   - an unknown property (`message`, `phone`);
   - a handle field containing a phone number or spaces;
   - an unknown event name.

   Each → 400, nothing stored. Pinned in Task 7.

5. **A suspended recipient:**
   - trying to go live → 409 `PAGE_SUSPENDED`;
   - their 10th tip confirming → no moment or reward;
   - withdrawing → still allowed.

   Pinned in Task 5.
