# PR-010 Release Rehearsal and Staging Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a staging setup (Vercel web + one Docker Compose VPS), and one release check that proves every journey on any copy without leaving visible data, plus backup/restore and rollback drills and runbooks. All of it is proven now on a local copy of the staging stack.

**Architecture:**

- **Staging layout:** Vercel serves the web app. The VPS runs Caddy, the API, the worker, Postgres and Redis.
- **Access:**
  - The preview password gates both hosts with one signed cookie scoped to `staging.<domain>`.
  - Each copy declares `RELEASE_KIND`.
  - A full check runs as a tagged rehearsal: its data is excluded from views and its account is deleted through the normal flow.
- **Images** are built from a commit SHA. Migrations are forward-only and compatible with the previous release.

**Tech Stack:**

- **Existing pins:** Node 24, pnpm, Turbo, Next 16, Nest 12, Drizzle, Postgres 16, Redis 7, Playwright 1.64.1.
- **New, pinned and registered:**
  - the `caddy` image;
  - `postgresql16-client` in the image;
  - the `rclone/rclone` image (optional off-site copy).

**Spec:** `docs/superpowers/specs/2026-10-19-pr010-release-rehearsal-design.md`

## Global Constraints

- **Money:** no real payments. `PAYMENTS_LIVE_ENABLED` stays `false`. The release check fails if `/health/release` reports live payments.
- **`RELEASE_KIND`:** `test` or `live`, default `live`. `POST /v1/release/runs` and the full check need `test`.
- **Append-only stays append-only:** ledger, status transitions, audit, issue notes and provider events get no update or delete path. Rehearsal data is excluded by filters only.
- **Preview gate:**
  - **When:** active only when `DEPLOYMENT_MODE=preview`.
  - **Cookie:** `__Secure-tipme_preview`, `Domain=<PREVIEW_COOKIE_DOMAIN>`, `HttpOnly`, `Secure`, `SameSite=Lax`, 12 hours.
  - **Ticket:** `<expiresMs>.<HMAC-SHA256(password, "tipme-preview:"+expires) base64url>`.
  - **Server key:** server-to-server calls send `x-tipme-preview-key: <HMAC(password, "tipme-preview-server")>`.
  - **API exemptions:** `/health/*`, `/v1/release/*` (bearer), `/v1/webhooks/*` (signed).
  - **Web exemptions:** `/__preview/*`, `/api/revalidate` (shared secret), and the Next static assets needed by the login page.
- **Secrets:** no secret values in the repository, logs or chat. `deploy/staging.env.example` holds names only.
- **Migrations:** remote migration requires `MIGRATE_CONFIRM_DATABASE=<database name>` to equal the URL's database, and a backup taken in the same deploy.
- **Backups:**
  - format: `pg_dump -Fc`, AES-256-GCM with `BACKUP_KEY` (32 bytes base64);
  - files: `tipme-<UTC timestamp>-<sha>.dump.enc` plus a `.manifest.json`;
  - kept 14 days.
- **Gates:**
  - format, lint, typecheck, test, build, `test:integration`, `test:e2e`;
  - plus the staging stack drills (`pnpm staging:local:*`) on this machine.

## Review Focus

1. **The preview gate reached through every door:** the API host directly (no cookie), `/v1/dev/inbox` without the cookie, path tricks (`//`, `%2e`), a forged or expired ticket, the server key on a non-server route. Each must be refused while `DEPLOYMENT_MODE=preview`.
   - Pinned in Task 1 (API) and Task 2 (web).
2. **The full check against a live copy:** a missing or `live` `RELEASE_KIND`, or a wrong bearer token, must refuse run creation, and the CLI must stop before creating anything.
   - Pinned in Task 3 and Task 6.
3. **Rehearsal data leaking into views:** rehearsal tips, visits, issues or pages in health/visibility metrics, the issue list or top pages.
   - Pinned in Task 3.
4. **A restore that looks fine but isn't:** a restore whose counts or ledger totals differ from the manifest, or a dump from the wrong key, must fail the drill.
   - Pinned in Task 5.
5. **Rolling back across a migration:** the previous release must run against the newer schema; deploy B (with migration) → roll back to A → full check passes.
   - Pinned in Task 7.

### Task 6: The release check (full and read-only)

**Files:**

- Create:
  - `tests/release/{playwright.config.ts, read-only.spec.ts, full.spec.ts, client.ts}`
  - `scripts/release-check.mjs` (CLI)
  - root script `release:check`
- **Read-only:** release info (not live payments; version if `--expect-version`); web home, `/@<handle>` if given, `/sign-in`: load, LCP ≤ 2.0 s throttled, axe; `/dashboard` and `/ops` carry noindex; the API `/v1/ops/me` without a session → 404.
- **Full:**
  1. creates a run;
  2. signs up a rehearsal recipient (pretend inbox) and makes the page live;
  3. a visitor opens `/@handle?src=qr`, tips with a message, and the payment succeeds;
  4. the recipient sees the tip and notification and withdraws everything;
  5. a second tip with `wrong-amount` → as the `release_check` staff (TOTP from env), the issue is visible with `includeRehearsal`; staff resolve it;
  6. health metrics are unchanged before and after;
  7. the account is deleted; the run is finished.
- [ ] Verify against the local e2e stack (`RELEASE_KIND=test`) and the local staging stack; the refusal case against `RELEASE_KIND=live`.

### Task 7: Deploy and rollback scripts, and the rollback drill

**Files:**

- Create:
  - `deploy/scripts/{deploy.sh, rollback.sh, lib.sh}`
  - `scripts/rollback-drill.mjs` (local)
- **Deploy:** `deploy.sh <sha>` does build → backup → migrate (guarded) → `up -d` → wait for health → read-only check; on failure, redeploy the previous SHA automatically. `rollback.sh` redeploys the previous SHA recorded in `/srv/tipme/releases/current` (and the list `releases/deployed`).
- [ ] Drill on the local staging stack: deploy A → deploy B (a test migration adding a nullable column) → roll back to A → full check passes.
