# PR-011 Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** close the PRD gaps from the 21 October audit that need no business decision (the user approved items 1–5): disaster recovery to RPO ≤ 15 min, alerts, error tracking, message reporting, sitemap/robots, handle renames with redirects, security scanning, load tests, real-user web vitals, OpenAPI.

**Spec:** the PRD (`docs/reference/TipMe_Master_PRD_v1.0.docx`) §§3.4, 5, 8, 10, 11, 12, 13, 14, plus the audit in chat (21 Oct). Item 1 (fix CI, merge PR #4) was already done by the hosting session; wiring the VPS waits for the user's server.

**Constraints:**

- Pretend money only.
- Append-only records stay append-only.
- New third-party tools are pinned and registered.
- No secrets in the repo.
- Work in the `feat/hardening` worktree; the main checkout belongs to the concurrent hosting session.

## Tasks

- [ ] **T1 Point-in-time recovery (RPO ≤ 15 min, PRD §13).**
  - Postgres WAL archiving (`archive_timeout=300`) to `/srv/tipme/wal`, plus a nightly physical base backup (`pg_basebackup`, encrypted) next to the existing logical dumps.
  - A PITR drill restores base backup + WAL into a scratch Postgres container and proves a row written after the base backup survives.
  - `GET /health/backups` reports the last logical/base backup and the archiver status (timestamps only).
- [ ] **T2 Alerts (PRD §14 Operations).** `staging-watch` workflow every 15 minutes:
  - API ready;
  - release info (no live payments);
  - backups fresh (logical < 26 h, base < 26 h);
  - WAL archiver healthy;
  - web reachable.

  Failure emails the repo owner (GitHub notifications); an optional webhook goes to Slack or Telegram. Thresholds are pure functions with tests.

- [ ] **T3 Error tracking (PRD §9, AGENTS PROPOSED Sentry).**
  - Optional `@sentry/node` in API and worker, off without `SENTRY_DSN`.
  - No request bodies, cookies, headers or user data; only server errors (5xx/unexpected).
  - Tests prove scrubbing and that nothing is sent when off.
- [ ] **T4 Message reporting (FR-010, §3.4 abusive message).**
  - A recipient reports a paid tip's message (abusive / spam / other), which opens a `message_reported` issue (severity account; admin reveals the text with a reason) and hides the message from their dashboard. They can also hide without reporting.
  - Reported messages never appear in summaries.
- [ ] **T5 robots and sitemap (FR-015).**
  - `robots.txt` disallows private areas, and everything on preview/staging copies.
  - `sitemap.xml` lists the marketing pages only (profiles stay noindex until D-06).
- [ ] **T6 Handle renames with redirects (FR-015, §3.4 "QR points to renamed handle").**
  - A recipient can change their handle in Settings.
  - Old handles become permanent aliases of that page (not claimable by others; at most 5 per page).
  - The API answers with the new handle; the web app redirects 308 to `/@new`, keeping `?src=qr`.
- [ ] **T7 Security scanning in CI (PRD §12).**
  - `pnpm audit --prod --audit-level=high`.
  - gitleaks (pinned image) over the repository.
  - Runs on every push.
- [ ] **T8 Load tests (PRD §10.1).** k6 (pinned image) against the local stack with thresholds from the PRD:
  - public profile p95 ≤ 200 ms;
  - checkout initialisation p95 ≤ 400 ms;
  - dashboard p95 ≤ 300 ms;
  - 5xx < 0.1%.
- [ ] **T9 Real-user web vitals (PRD §10.1, §11).**
  - `web_vital` analytics events (LCP/INP/CLS/FCP/TTFB, value, page kind), honouring GPC/DNT and stored on no device.
  - The admin Overview shows p75 against budgets: LCP ≤ 2.0 s, INP ≤ 150 ms, CLS ≤ 0.05.
- [ ] **T10 OpenAPI 3.1 (PRD §8).**
  - Generated from the zod contracts into `docs/api/openapi.json`.
  - A test proves every API route is documented, and nothing extra is.
  - CI fails when the file is stale.
- [ ] **T11 Docs and verification.**
  - Fix the decision-number mix-up (messaging provider ≠ D-08; add D-11).
  - ADR-0012, runbooks, register entries, `docs/PR-011-VERIFICATION.md`.
  - Final gate, fresh review, fix pass.

## Review Focus

1. A PITR restore that silently loses data (wrong target, missing WAL).
2. Error reports carrying personal data (bodies, cookies, phone numbers, messages).
3. Reporting or renaming as a way to reach someone else's page or message.
4. An old handle captured by another person (impersonation) or a redirect loop.
5. Web-vitals or report endpoints accepting free text or identifiers.
