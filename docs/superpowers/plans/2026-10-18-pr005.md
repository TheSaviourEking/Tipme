# PR-005 Money Records Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Database records that prove a tip was paid (verified provider evidence) and that the recipient's share was paid out, using a balanced, append-only, custody-neutral double-entry ledger, with no real money.

**Architecture:** Pure rules (money, mock fees, state machines, balanced posting builders) live in a new `packages/domain`. A new `packages/database` holds the Drizzle schema, SQL migrations (including triggers that enforce append-only history and balanced books), and transactional operations that combine domain rules with Postgres row locks in one transaction each. The worker gains an outbox relay that moves committed events to BullMQ.

**Tech Stack:** Node 24.22.0, TypeScript strict, Postgres 16, drizzle-orm 0.45.3, drizzle-kit 0.31.11, pg 8.23.1, uuid 14.0.2 (v7), BullMQ 6.3.11, `node --test`.

**Spec:** `docs/superpowers/specs/2026-10-18-pr005-money-records-design.md`

## Global Constraints

- Exact pins: `drizzle-orm` 0.45.3, `drizzle-kit` 0.31.11 (dev), `uuid` 14.0.2; reuse `pg` 8.23.1, `@types/pg` 8.23.1, `zod` 4.6.7, `bullmq` 6.3.11, `ioredis` 5.11.1. Any other new dependency needs a ledger ruling and an ADR entry.
- Money: `bigint` minor units plus a 3-letter ISO currency (`/^[A-Z]{3}$/`) everywhere. Postgres `bigint`, Drizzle `bigint({ mode: 'bigint' })`. No `number` for money, no `numeric`, no floats. JSON boundaries carry amounts as decimal strings.
- Status names exactly as the PRD: tip `DRAFT, AWAITING_PAYMENT, PENDING_VERIFICATION, SUCCEEDED, FAILED, CANCELLED`; attempt `CREATED, INITIATED, PENDING, VERIFIED_SUCCEEDED, VERIFIED_FAILED, EXPIRED, UNKNOWN`; payout `REQUESTED, PROCESSING, PAID, FAILED, REVERSED`.
- Never the word "wallet" for balances: use `recipient_payable`.
- `MOCK_FEE_POLICY_V0` is labelled "not an approved commercial policy (D-05)" in code and docs.
- Tip message text never goes into logs, spans, outbox payloads or job data.
- Migrations and seeds refuse any `DATABASE_URL` host other than `localhost`, `127.0.0.1` or `::1`.
- IDs: UUIDv7 from `uuid` v7, generated in the application.
- BullMQ custom job IDs must not contain `:`; outbox dedupe keys use `.` separators (`tip.succeeded.<tipId>`).
- No Git repository: each task ends with a checkpoint (format of touched files, `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm test:integration` when the task touches Postgres), not a commit.
- Node 24.22.0 first on `PATH` (`export PATH=$HOME/.npm/_npx/fee7060b69ab3f2d/node_modules/node/bin:$PATH`); Docker Postgres and Redis running (`pnpm infra:up`).

## Review Focus

1. **A success event after a verified failure** (the money may really have been captured): there is no state change, the event is kept, and an outbox `payment.conflict` is written for operations. Never silently ignored (Task 4).
2. **Payout of a tip that is not this recipient's, not yet succeeded, or already in an active payout** is rejected. A FAILED payout releases its tips for a new payout (Task 5).
3. **A quote for a hidden or suspended profile** fails like a missing profile (`PROFILE_NOT_FOUND`), so it reveals nothing (Task 3).
4. **`bigint` reaching JSON:** outbox payloads and the proof read model carry amounts as strings; `JSON.stringify` never throws on a `bigint` (Task 4 and Task 5).
5. **`pnpm db:migrate` with a remote `DATABASE_URL`** refuses before opening any connection (Task 2).

**Files:**

  - internal `postLedgerTransaction(tx, { operationType: 'payment' | 'payout', operationKey: string, currency: string, tipId?: string; payoutId?: string; lines: LedgerLine[]; traceId: string | null }): Promise<{ transactionId: string; created: boolean }>`: upserts accounts (`code`, `currency`, `profile_id`); `operation_key` conflict → returns the existing ID with `created: false` and inserts no entries.
  - `interface PaymentEvent { provider: string; providerEventId: string; eventType: 'payment.succeeded' | 'payment.failed' | 'payment.pending'; attemptId: string; providerReference: string; amountMinor: bigint; currency: string; providerFeeMinor: bigint; signatureVerified: true; payload: unknown; traceId?: string | null; now?: Date }`
  - `recordProviderEvent(db, event): Promise<{ outcome: 'applied' | 'duplicate' | 'ignored' | 'mismatch' | 'conflict'; tipStatus: string; attemptStatus: string }>`. In one transaction:
    1. Insert the event (payload hash = SHA-256 of `JSON.stringify(payload)`); a conflict → return `duplicate` with current statuses.
    2. Lock the attempt and its tip `FOR UPDATE`; set `provider_reference` when null.
    3. **succeeded:** if the attempt is already `VERIFIED_SUCCEEDED` → `ignored`. If `VERIFIED_FAILED` or `EXPIRED` → `conflict` plus outbox `payment.conflict`. If amount ≠ quote `payer_total_minor` or currency differs → attempt → `UNKNOWN` (if allowed), outbox `payment.mismatch`, `mismatch`. Otherwise attempt → `VERIFIED_SUCCEEDED`, tip → `SUCCEEDED` (`completed_at`), post `payment.<attemptId>` with `actualProviderFeeMinor = event.providerFeeMinor`, outbox `tip.succeeded` with payload `{ tipId, profileId, currency, grossMinor, recipientNetMinor }` as strings → `applied`.
    4. **failed:** if already succeeded → `ignored` (no downgrade). Else attempt → `VERIFIED_FAILED`, tip → `FAILED`, outbox `tip.failed` → `applied`.
    5. **pending:** attempt → `PENDING` and tip → `PENDING_VERIFICATION` when allowed, else `ignored`.
    6. Transitions are recorded with `cause: 'provider_event'` and `providerEventId`; set `processed_at` and `processing_outcome`.
