# PR-006 Mock Provider Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A provider interface and a signed-webhook mock provider that drives the PR-005 money records through all nine agreed scenarios, plus reconciliation of unanswered payments, with no real provider or money.

**Architecture:** A new framework-free `packages/payments` defines `PaymentProvider`, webhook signing and the Redis-backed mock with its scenario simulator. The API gains a raw-body, signature-verified `POST /v1/webhooks/mock` that routes verified events to PR-005 operations (or to a durable unmatched table). The worker gains a repeatable reconciliation job; a developer command runs scenarios end to end.

**Tech Stack:** Existing pins only: Node 24.22.0, Nest 12.1.3 (`rawBody`), drizzle-orm 0.45.3, ioredis 5.11.1, BullMQ 6.3.11 (`upsertJobScheduler`), zod 4.6.7, node `crypto` (HMAC-SHA256, `timingSafeEqual`).

**Spec:** `docs/superpowers/specs/2026-10-18-pr006-mock-provider-design.md`

## Global Constraints

- No new runtime dependencies (ledger ruling needed otherwise).
- Signature header exactly `x-mock-signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<raw body>">`; secret `MOCK_PROVIDER_WEBHOOK_SECRET` (≥ 32 chars); tolerance 300 s past and 300 s future; constant-time compare; verification on the raw bytes before any JSON parsing.
- Webhook types exactly: `payment.pending`, `payment.succeeded`, `payment.failed`, `payout.processing`, `payout.paid`, `payout.failed`. Wire amounts are decimal strings of minor units.
- Mock fee = `(amount × 150 + 5000) / 10000` (same rounding as `MOCK_FEE_POLICY_V0`).
- Startup refuses `PAYMENT_PROVIDER=mock` with `NODE_ENV=production`, and any `PAYMENTS_LIVE_ENABLED` other than `false`.
- Reconciliation: every 60 s (`RECONCILE_INTERVAL_MS`, default 60000), attempts older than 120 s (`RECONCILE_MIN_AGE_MS`, default 120000), batch 50, event IDs `reconcile.<attemptId>.<status>`; `not_found` older than 30 min → outbox `payment.unresolved` once per attempt. Never calls `initializePayment`.
- Never log raw bodies, signatures, secrets or payloads; log reasons and IDs only.
- Scenario names exactly: `succeed`, `decline`, `pending-then-succeed`, `duplicate`, `out-of-order`, `wrong-amount`, `no-reply`, `forged`, `payout-paid`, `payout-failed`.
- No Git: each task ends with a checkpoint (format, lint, typecheck, test, and `test:integration` when Postgres/Redis are touched).

## Review Focus

1. **A webhook whose signature is valid but whose body is not valid JSON or fails the schema** → 400, nothing stored (Task 3).
2. **A verified webhook claiming an `attemptId` whose provider reference belongs to a different attempt** → matched by reference only; the claimed ID is ignored (Task 3).
3. **The database is down when a verified webhook arrives** → 503, so the provider retries; no partial rows (Task 3).
4. **Reconciliation running in two workers at once** → each attempt is reconciled at most once per answer (deterministic event IDs make the second a duplicate) (Task 4).
5. **The same unknown-attempt webhook delivered twice** → one `unmatched_provider_events` row (Task 3).
